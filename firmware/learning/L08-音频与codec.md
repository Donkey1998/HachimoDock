## 零基础补给站

| 术语 | 一句话解释 |
|---|---|
| 采样率 | 每秒对声波"拍照"多少次。16kHz=每秒 16000 个样本——按采样定理能还原 8kHz 以内的声音，人声频带恰好够（CD 是 44.1kHz 因为要装音乐的高频） |
| 位深 | 每个样本用多少位存。16bit=每秒的音量刻度有 65536 格，人耳已听不出颗粒感 |
| 单声道 | 一个声道（一路波形）。电话、语音助手都是单声道；立体声是两路 |
| PCM / WAV | PCM=原始数字音频（就是一串样本值）；WAV=PCM 加个文件头（采样率、长度）的封装，≈"裸流"与"容器"的关系 |
| codec 芯片 | 编解码器：内部是 ADC（麦克风模拟→数字）+ DAC（数字→扬声器模拟）。CPU 给它数字流、它管物理世界 |
| 回声（声学） | 扬声器放出的声音经空气/桌面反弹进麦克风。全双工语音设备的头号敌人——设备会"听见自己说话" |
| 环形缓冲 / 水位 | 一圈首尾相接的缓冲区，读写各走各的指针；"水位 200ms"=攒够 200ms 数据才开播，吸收网络抖动，≈ 视频网站的缓冲条 |

**为什么音频优先级最高**：人耳对"断续"极其敏感（一帧渲染慢 50ms 看不出，音频断 50ms 立刻刺耳）——这是第03课优先级表的物理根源。

## 讲解

### 8.1 数字音频的基本形状

模拟声音进芯片前要数字化：**16kHz 采样率、单声道、16bit**（每秒 16000 个样本，每样本 2 字节）。硬件上分两条流：

- **I2S 总线（数据流）**：MCLK=GPIO13、BCLK=GPIO12、WS=GPIO10、DOUT=GPIO9（芯片→codec，播放）、DIN=GPIO11（codec→芯片，录音），控制器 1。DMA 3 描述符 × 160 帧 ≈ 30ms 缓冲。
- **I2C 总线（控制流）**：配 codec 芯片的音量、增益、采样率——就是第06课那条总线上挂的 0x18 和 0x40。

**esp_codec_dev 组件**把这两条流封装成统一接口：`esp_codec_dev_open/read/write/set_out_vol`——你操作的是"编解码设备"，不用管底下芯片型号。类比安卓的 `AudioTrack/AudioRecord` 屏蔽底层 HAL。

### 8.2 双 codec 与探测回退（`main/pet_p4_audio.c:682-706`）

这块板可能有**独立采集芯片 ES7210**（地址 0x40，:30）也可能没有；ES8311（0x18，:31）一定有（播放用）。初始化逻辑：

```
i2c_master_probe(0x40) 成功？
 ├─ 是 → ES7210 当麦克风（增益 30dB）+ ES8311 当喇叭   ← 最佳方案
 └─ 否 → ES8311 双工模式：一颗芯片同时当麦+喇叭        ← 降级方案（BSP 的 duplex init）
```

第06课 GT911 双地址探测的同款思想又出现了：**硬件配置不确定时，探测后选择策略**。ES8311 双工时增益降到 24dB（:105-112）——一颗芯片身兼两职，参数要保守。

### 8.3 两个音频任务与半双工门控

`pet_p4_audio`（采集，`audio.c:720`）和 `pet_p4_playback`（播放，:744）都是优先级 18、绑 core 0——全系统最高优先级（音频断流人耳立刻听得出）。

**采集路径**：平时任务挂起等**任务通知**（第03课），按下语音键被唤醒 → `esp_codec_dev_read` 读 PCM → 过 AFE（见 8.4）→ base64 编码进 `audio/chunk` JSON 上行。

**播放路径**：消费请求队列——整段 WAV（先校验头再读 PCM）或流式环形缓冲（对话 TTS/音乐，起播水位 200ms 攒够才开播，防网络抖动）。音乐模式会把 codec 重开为 48kHz（:1002）——语音 16k / 音乐 48k 的动态切换。

**半双工门控**（:135-146，`playback_gates_capture`）：形象正在说话（播放中）时**丢弃麦克风帧**。这是 AEC 失效时的保底：宁可漏听，不要把扬声器声音当成人声传上去。

### 8.4 回声消除：参考信号的妙用（`main/pet_p4_audio_frontend.c`）

问题：设备一边外放 TTS 一边录音，麦克风会把扬声器声音也录进去，PC 端 ASR 会把宠物自己的话听成用户说话。

AEC（Acoustic Echo Cancellation，esp-sr 组件的独立算法 API，创建代码在 `main/pet_p4_audio_frontend.c` 的 AFE 初始化函数里）的原理：给它两路信号——**麦克风信号** + **播放了什么（参考信号）**，它把两者中相关的成分（即回声）从麦克风采音里减掉。

**参考信号从哪来是设计关键**：本项目直接在播放路径上分叉——每次 `esp_codec_dev_write` 播放的同时，把同一份 PCM 喂给 AEC 作参考（`pet_p4_audio_frontend.c:89-105`）。这样参考信号和实际发声**天然同步**（含播放缓冲延迟），消除效果最好。

三个配套算法各司其职：AEC 去回声、NS 去噪声、VAD 判断"有没有人在说话"（省流量，静音不上传）。全部失败时降级到 8.3 的半双工门控——注意这个**降级链条**：AEC 挂了→半双工；半双工再差也比"宠物自说自话听自己"强。

### 8.5 一图总结

```
麦克风 ──ES7210/ES8311──I2S──> 采集任务 ──> AEC(减去参考) ──> NS/VAD ──> audio/chunk JSON ──> USB 上行
扬声器 <──ES8311──I2S── 播放任务 <── WAV/TTS/音乐队列
                              └──────┬──────┘
                              同一份 PCM 喂给 AEC 作参考信号
```

4. **💭思考**：为什么参考信号取"送给 codec 的数字 PCM"而不是"麦克风重新采一份扬声器声音"？
5. **💭思考**：语音用 16kHz、音乐切 48kHz。如果语音也用 48kHz，AEC/上行带宽各会发生什么变化？

## 自测与参考答案

- **练习4**：数字 PCM 是"无损的播放意图"，干净、已知；用麦克风采回扬声器声音混入了环境噪声和房间混响，AEC 还得先估一遍声学路径，效果差得多。
- **练习5**：AEC/NS/VAD 按 16k/20ms 帧设计，48k 内存和计算量×3，P4 上跑不动或被迫降级；上行带宽也是 3 倍（base64 后再 ×4/3）。人声频带 8kHz 就够，16k 是性价比点。
