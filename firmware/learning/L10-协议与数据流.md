## 零基础补给站

| 术语 | 一句话解释 |
|---|---|
| 线协议（wire protocol） | 两个程序隔着线对话时约定的"消息格式+礼仪"。HTTP 是浏览器和服务器之间的线协议，本项目的 JSONL 是 PC 和固件之间的 |
| JSONL | JSON Lines：一行一条完整 JSON。流式处理友好——收到一行处理一行，不用等整个文件（对比：一个巨型 JSON 数组必须全部收到才能解析） |
| base64 | 把任意二进制编码成 64 个安全字符的方案，3 字节→4 字符（膨胀 33%）。**为什么需要它**：JSON 规定值必须是文本，音频 PCM 是二进制——想放进 JSON 就得先套一层 base64 |
| ACK / NACK | 肯定应答/否定应答，串口和 TCP 世界的老传统："收到，没问题"/"收到，但有错" |
| requestId / correlation id | 请求带上编号、应答带着同一个编号回来——异步世界里把"问题"和"答案"配对的挂钩（JS 的 Promise、Retrofit 的 callId 同一思想） |
| schema 版本 | 协议的"格式版本号"。双方先对表：版本不合就不能贸然通信——防止新 PC 对旧固件发它看不懂的字段 |

## 讲解

### 10.1 protocol.md 的读法：别通读，按需查

59KB 的协议规范是**字典**不是教材。按这个顺序读三节：

1. **Handshake 握手节**：`hello` 消息——设备上电/USB 挂载后主动上报的自述，含固件版本、buildId、git sha、协议 schema 版本、**chipRevision**（PC 据此选 v1/v3 升级镜像，第02课伏笔回收）
2. **状态与对话节**：`state/<agent>`（Agent 状态推送）、`session/current`、`speech/text`（让宠物说话）
3. **输入节**：`input/config`（PC 下发按键映射，存 NVS）、`input/event`（固件上报按键/触摸）、触摸手势定义

每条消息的形状都是一行 JSON：`{"topic": "...", "payload": {...}}`（wire 协议名 `pet-usb-jsonl-v3`，常量在 `main/pet_p4_protocol.c:49`）。

### 10.2 分发器的设计注释（`main/pet_p4_protocol.c:1-15`）

这个 2600 行文件的开头注释是全项目最好的"模块说明书"，务必逐句读：

```c
/*
 * [Input]  JSON-line control/state envelopes from USB-UART and native USB.
 * [Output] validated runtime updates, ACK/NACK responses, persisted input
 *          configuration snapshots, transfer routing, ...
 * [Pos]    shared ESP32-P4 protocol dispatcher.
 * [Sync]   If this file changes, update firmware/protocol.md and .folder.md.
 */
```

四行标签的约定：**输入什么、输出什么、这文件在系统中的位置、改动时要同步更新什么文档**。读任何大文件先找这种注释（[第12课](L12-进阶专题导读.md)的五个大文件都有）。

### 10.3 消息处理的三件套：topic 路由 / ACK-NACK / requestId

**topic 路由**：每条进来的消息按 `topic` 字符串查表分发到对应处理函数——和安卓的隐式 Intent 按 action 分发一个思路。`protocol.c` 的主体就是这张"topic → handler"表和各 handler。

**requestId + ACK/NACK**：PC 的请求带 `requestId`，固件处理完回 `ACK`（成功，带原 requestId）或 `NACK`（失败，带原因）。这样 PC 能：① 知道哪条请求有了结果（异步关联）② 区分"没收到"和"收到但拒绝"。没有它，PC 只能靠超时瞎猜。

**schema 版本**：握手时双方核对协议 schema（当前 7），不一致则拒绝危险操作——固件和 PC 端各自升级不同步时的保护网。

### 10.4 两条必背数据流

**上行（设备 → PC）**：
```
按键按下 → pet_p4_input 任务 5ms 轮询捕获（第05课）
  → input_core 消抖/解码 → 事件队列
  → 主循环 pet_p4_input_process 按映射表转换（NVS 里的 pet_input 配置）
  → input/event JSON → 来源路由 → USB 下发
```

**下行（PC → 设备）**：
```
state/claude-code JSON 到达（任一 USB 通道，第09课）
  → RX 任务 → g_protocol_queue → pet_p4_protocol 任务（持 g_state_mutex）
  → topic 路由到 handler → 更新运行时状态
  → 主循环 50ms 渲染周期取状态画帧（第07课管线）→ 屏幕更新
```

把第05/07/09课的知识串在一条线上——这就是"全局地图"毕业考。

### 10.5 契约测试：协议的防漂移护栏

`tests/protocol_contract_test.py`（仓库根目录直接跑）做的是**静态契约检查**：扫描固件源码、protocol.md 文档、PC 端代码三方，断言 topic 名、字段、版本号一致。任何人改了协议忘了同步文档或 PC 端，CI 就红。

这解决的是多端协同的千古难题：**接口文档靠人记必漂移，靠测试锁才可靠**。你写安卓时 AIDL 改了接口、另一个 module 没重编译还能编过——同类问题在固件↔PC 之间靠契约测试兜住。

## 练习

1. **📍阅读**：读 protocol.md 的 Handshake 节，列出 `hello` 消息里设备上报的字段清单。找到 `chipRevision` 的编码规则（v1 和 v3 各是什么范围）。
2. **📍阅读**：精读 `pet_p4_protocol.c:1-15` 头注释，然后对照 [Output] 描述里的每一项（ACK/NACK、配置快照、传输路由……）在文件里 grep 对应的实现关键词，确认"文档说的代码里真有"。
3. **🔧动手**：经串口（UART0 波特率 4,000,000；或桌面端的调试入口）手写发一条 `speech/text` 消息让宠物说"我学会了"。再发一条故意写错 topic 的消息，观察固件回了什么（NACK 长什么样）。
4. **🔧动手**：触发 `debug/screenshot` 拿到一张截图（第07课练习4 做过的话对比两次内容）。
5. **💭思考**：`widget/data` 是 PC 每 2 秒推一次的实时快照（股票、待办）。为什么设计成"PC 推"而不是"设备每 2 秒拉"？

## 自测与参考答案

- **练习1**：字段含 fw 版本、buildId、gitSha、protocolSchema、chipRevision 等；v1 = 修订 1–199、v3 = 300–399（major×100+minor 编码）。
- **练习3**：错误 topic 一般回 NACK（带原因），或被静默忽略——以实际行为为准记进笔记；能收到 ACK 说明链路通。
- **练习5**：数据源（行情/待办）在 PC 侧，设备拉还得先"请求-应答"一轮且设备不知道数据何时变；PC 推让设备实现最简单（收就显示），也天然控频。**谁有数据谁负责推送**是跨端协议的常用分工原则。
