# 第04课 · 启动序列与主循环

> 预计用时：1.5 小时 · 前置：[第03课](L03-FreeRTOS最小概念集.md)
> 路径约定：相对 `firmware/` 目录。本课的代码主战场是 `main/pet_p4_main.c`（855 行，建议全文通读一遍——它是全项目最好的地图文件）。

## 学习目标

1. 能按顺序说出 `app_main` 的 17 步初始化及其设计意图
2. 理解"尽力而为（best-effort）初始化"模式的动机与代价
3. 看懂主循环的多周期节拍设计

## 零基础补给站

| 术语 | 一句话解释 |
|---|---|
| bootloader | 芯片上电后最先跑的一小段程序，负责把"真正的应用"（我们的固件）从 Flash 搬到 RAM 并跳过去——类似安卓的开机引导 |
| `app_main` | ESP-IDF 约定的应用入口函数，bootloader 收尾后从这里开始执行你的代码（≈ 安卓的 `Application.onCreate`） |
| RAM / SRAM | 断电即丢、速度快的内存。变量、任务栈、帧缓冲都住这里 |
| PSRAM | 外挂的大容量 RAM（本板 32MB），速度比片内 SRAM 慢但容量大——大块头数据（视频帧）住这里 |
| Flash | 断电不丢的存储。程序本体、NVS、SPIFFS 都在 Flash 的不同分区里 |
| NVS | "非易失键值存储"= Flash 上的 SharedPreferences。**为什么需要它**：Flash 只能按页擦除再写（不能直接覆盖写一个字节），NVS 组件帮你管理这堆麻烦并做磨损均衡 |
| fail-fast / 尽力而为 | 两种错误哲学：失败立刻崩溃（方便发现问题）vs 失败降级继续跑（保可用性）。嵌入式设备用户没法重启你，所以偏后者 |

**读启动代码的心法**：别急着懂每行，先问三个问题——这一步**失败会怎样**？为什么排在这个位置？它在为后面的哪一步铺路？本课的 17 步表格就按这个思路读。

## 讲解

### 4.1 启动序列（`app_main`，`main/pet_p4_main.c:590-747`）

| # | 步骤 | 位置 | 设计意图 |
|---|---|---|---|
| 1 | `pet_p4_lcd_prepare_boot()` 灭背光 | :602 | **第一件事**：屏未初始化前背光亮着=显示花屏/蓝屏 |
| 2 | `nvs_flash_init()` | :606 | 键值存储（按键映射等） |
| 3 | PSRAM 缓冲 + 4 互斥量 + 协议队列 | :607-643 | 先建基础设施 |
| 4 | `init_storage()` 挂 SPIFFS | :617 | 失败**不格式化**（格式化会抹掉用户组件） |
| 5 | 诊断 / 设备 ID / 状态初始化 | :622-631 | |
| 6 | 创建 `protocol_worker_task` | :647 | 先有消费者，再开生产者 |
| 7 | 组件运行时 + 内置资产加载 | :654-664 | |
| 8 | USB-Serial-JTAG、UART0 驱动 | :665-666 | |
| 9 | `pet_p4_input_init()` 按键+ADC | :667 | |
| 10 | `pet_p4_lcd_init()` DSI+面板 | :668 | |
| 11 | `pet_p4_touch_init()` GT911 | :669 | LCD 失败则跳过（依赖 I2C 与"屏在"） |
| 12 | `pet_p4_audio_init()` codec+任务 | :674 | |
| 13 | 首帧渲染 + `pet_p4_lcd_reveal()` 亮屏 | :680-687 | **渲染成功才亮屏**，用户永远看不到黑屏到花屏的过程 |
| 14 | I2C 扫描诊断 / OTA / 原生 USB | :691-706 | |
| 15 | UART/USB RX 任务 | :718-731 | |
| 16 | `pet_p4_afe_init()` 回声消除 | :737 | **最后**：源码注释写明要让显示/USB 任务先把 RAM 占住（esp-sr 模型吃内存大） |
| 17 | 发 `hello` 握手 → 进主循环 | :739 起 | |

值得背下来的三处对称设计：**灭屏（步骤1）↔ 亮屏（步骤13）**；**消费者先建（步骤6）↔ 生产者后建（步骤15）**；**重要性低的先初始化可被跳过 ↔ 最重要的协议通路最优先保障**。

### 4.2 尽力而为初始化（best-effort init）

注意步骤 11-12 的模式：ES7210 不在位→回退 ES8311 双工；AEC 初始化失败→降级半双工；LCD 失败→跳过触摸但**继续跑**。所有外设 init 失败只 `ESP_LOGW` 警告，不 panic 不重启。

为什么？因为**USB 通信和 OTA 回滚判定是生命线**：哪怕屏幕坏了，设备还得能被 PC 识别、还能刷回好固件。如果 init 失败就死机，一次外设故障就变成砖。

代价：每个模块都要处理"自己可能没初始化成功"的状态，代码里到处是 `if (!g_xxx)` 防御判断。这是可靠性的常规交换。

### 4.3 主循环节拍（`main/pet_p4_main.c:748-853`）

主循环 `while(true)` 每 **1ms** 一圈（`PET_P4_MAIN_LOOP_DELAY_MS`，:58），但内部按不同周期触发工作：

| 周期 | 工作 | 为什么是这个周期 |
|---|---|---|
| 50ms | 渲染一帧（20fps） | 动画流畅够用，省 CPU 给音频/H264 |
| 500ms | 传输进度屏刷新 | 传文件时的进度条，人眼不需要更快 |
| 1000ms | LCD 保活信号 | 防面板异常的兜底心跳 |

所有共享状态都在第03课的互斥量保护下访问。**1ms 圈 + 分频触发**是很常见的嵌入式主循环模式（对比你熟悉的安卓 `Handler.postDelayed`，这里是手动分频）。

2. **📍阅读**：看步骤 4 的 `init_storage()`（:501-509 附近），找到"失败不格式化"的具体判断代码。
3. **🔍追踪**：在 `main/pet_p4_main.c` 中找一个"初始化失败继续跑"的分支（如 LCD 或触摸失败的处理），抄下代码，说明失败后系统行为如何降级。
4. **💭思考**：如果把 AFE 初始化挪到步骤 3（最早），可能出什么问题？提示结合 `pet_p4_audio_frontend.c:14-16` 附近的注释（它解释了为什么不用 WakeNet 大模型）。
5. **💭思考**：主循环 1ms 跑一圈，但渲染 50ms 一次。其余 49 圈它在做什么？这种"忙一圈睡 1ms"和"睡 50ms 干一次"两种写法各有什么优缺点？

## 自测与参考答案

- **练习3**：示例——`pet_p4_touch_init()` 在 LCD 初始化失败时直接返回，`pet_p4_input` 等模块继续运行；触摸事件不再产生，但按键、USB、OTA 全部正常。
- **练习4**：esp-sr 的 AEC/模型内存占用大，先初始化会把 RAM 占住，后面显示双缓冲/USB 缓冲可能分配失败；本项目 OTA 槽只有 2.5MiB，所以连 WakeNet 都装不下，只用了独立算法 API。
- **练习5**：其余圈在做节拍检查、传输超时判断、RX 健康检查。1ms 圈响应快（如传输中断检测）但 CPU 略耗；50ms 睡法省电但 50ms 内的紧急事件要等下一拍。本项目选前者因为要兼顾多个不同周期的事件。
